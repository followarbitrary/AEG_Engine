# AEG FlowGraph：节点目录与扩展机制

[返回架构总览](<../AEG FlowGraph Architecture.md>)

本分册描述节点来源与功能契约；当前可执行目录和 `allow_add_passes` 规则属于 Frame/Render
profile。Logic/Flow 的 Feature、Flow、State、Transition、Event 和 FunctionCall 目录类型
遵循同一 TypeCatalog 身份规则，但编辑与运行开放条件以架构修订规格 §7/§10 为准。输入来源
状态、资源版本、完成点、持久化和模块回流的规范定义见 [作者与执行契约](authoring-and-execution-contract.md)。

“节点从哪里来”和“节点具体做什么”必须分开设计：节点来源决定它是否出现在节点库、由谁维护、是否可以编辑；节点契约决定它有哪些输入输出、输入数量、参数、资源要求和运行行为。编辑器不能通过节点名称、C++ 类名或画布位置猜测功能。

## 1. 节点来源分类

### 1.1 引擎系统节点

由 AEG Engine 提供，负责图的边界和运行上下文：

- `Frame Input`、`View Input`、`World Snapshot`、`Frame Context`。
- `Graph Input`、`Graph Output`、`Main Color Output`、`Debug Output`。
- 平台资源、History、Imported Resource、Queue/Stage 上下文。
- 基础的类型转换、Copy、Resample、Join 等通用节点。

这类节点可以被折叠、替换合法绑定或配置参数，但部分节点不能删除，因为没有它们图无法获得运行上下文。它们的来源显示为“Engine”，版本随引擎发布。

### 1.2 引擎领域模块节点

由 Render、Physics、Audio、Logic、Stream 等领域模块注册：

- Pipeline 类型。
- Feature 类型。
- RenderPass/Pass 类型（仅 Frame/Render profile）；Logic/Flow 可注册 StateMachine/Flow 定义和 Transition 契约。
- 领域专用 Artifact、Resource、Adapter 和组合节点。

模块节点的实现由模块代码负责，编辑器只读取节点契约。模块加载失败时，作者图仍保留未知节点、原始参数和连接，并显示“模块缺失”；不能把缺失模块当作空节点或删除。

### 1.3 游戏项目模块节点

由具体游戏项目提供，例如：

- 游戏专用的 Volumetric Fog Feature。
- 游戏专用的 Outline Pass。
- 项目定义的 LightCluster Artifact。
- 项目专用的 Material/Color/Visibility Adapter。

项目节点与引擎节点使用同一套 TypeCatalog 和节点契约。项目节点可以只在当前项目、目标平台或指定 Pipeline 中出现；节点库不扫描源码目录来推断可用节点。

### 1.4 编辑器创建的空白自定义节点

FlowGraph 的 **Create Empty Node** 是一个明确的作者动作，不是把缺失模块伪装成可用节点。编辑器按当前
profile 创建 Feature 节点；Frame/Render 兼容 profile 还可创建 Pipeline/Pass 投影视图。Logic/Process
的 StateMachine/Transition 先作为 Feature-owned opaque extension 保存，不假装现有 TypeCatalog 已有
独立 Flow kind，同时创建节点实例并写入 `.aegpipe` 的扩展记录。该类型没有执行工厂、端口或参数，节点
卡片显示为空白/未实现状态；重新打开作者图时目录从扩展记录恢复，之后必须通过自定义节点脚手架补充契约、
源码和模块注册，再刷新目录并进入可执行状态。

空白 Pass 创建时，编辑器会在同一份作者目录草稿中记录所属 Feature 对该 Pass 类型的允许关系；它不会改变引擎模块的永久元数据。用户取消或撤销实例创建不会删除已经生成的类型定义，避免同一类型的其他实例失去来源。

### 1.5 图资产节点

用户把一组节点转换为 Feature、CompositePass 或 Macro 后，形成可复用图资产。资产节点有自己的版本、输入/输出接口、缩略图、说明和依赖列表。

图资产节点不是复制一份内部实现到每个实例，而是引用一个子图定义；每次放入画布创建独立实例，实例拥有自己的参数和数据绑定。子图接口变化必须进入迁移流程。

### 1.6 插件/扩展包节点

未来可以允许插件包提供节点，但仍必须通过模块注册和 TypeCatalog 进入编辑器。插件不能通过运行时反射临时向已打开的图注入端口，也不能依赖编辑器扫描任意动态库来显示节点。

## 2. 不应该直接成为节点的对象

以下对象不能仅因为在运行时存在就自动出现在节点库：

| 对象                             | 原因                                   | 正确展示方式                   |
|----------------------------------|----------------------------------------|--------------------------------|
| Scheduler 内部 Task              | 用户不拥有稳定输入输出和可保存身份     | Runtime Inspect 只读节点       |
| GPU Handle、RHI Command、Barrier | 设备相关且不能作为项目作者语义稳定保存 | Pass/Resource 契约的高级诊断   |
| 编译器临时节点                   | 每次编译可能变化，不能作为作者资产身份 | Compile Plan/Runtime Inspect   |
| 未暴露的 CompositeFeature Part   | 所有权和生命周期属于父 Feature         | Feature 黑盒的内部来源         |
| 任意 C++ 类或函数                | 缺少数据类型、参数范围和运行契约       | 由开发者封装成注册节点后再出现 |
| 只改变画布布局的 Reroute/Comment | 不产生数据、不改变执行                 | 编辑器视图对象                 |

## 3. 节点注册入口

AEG 当前已有 `TypeCatalogEntry`、`ParameterDescriptor`、`PortDescriptor`、`AuthoringDeclaration`、`allowed_pass_types` 和 `allow_add_passes`。FlowGraph 将它们视为节点目录的基础，并扩展出完整的 Dataflow Node Contract。

推荐流程：

```text
模块声明节点
    ↓
TypeCatalog 注册与契约校验
    ↓
按图层、领域、目标和权限生成节点库
    ↓
用户创建节点实例
    ↓
端口/参数/资源验证
    ↓
编译器把实例映射到运行实现
```

模块注册时需要同时提供：稳定 TypeId、版本、显示信息、适用图层、领域、端口、参数、声明能力和运行实现来源。注册成功只表示契约完整，不表示每个目标设备都能运行；目标能力在 Compile/Prepare 阶段继续校验。

## 4. Node Contract 的组成

### 4.1 身份与来源

| 字段                 | 作用                                     |
|----------------------|------------------------------------------|
| TypeId               | 稳定节点类型身份，不随显示名改变         |
| Version              | 节点契约版本，影响迁移和编译             |
| OwnerModule          | 提供实现和目录的模块                     |
| DisplayName/Category | 节点库显示名称和分类                     |
| Description          | 面向游戏开发者的用途说明                 |
| Documentation        | 详细说明、示例、限制和性能提示           |
| Icon/Color           | 视觉识别，不承担类型判断                 |
| GraphKinds           | 可出现在 Feature Graph 及其 profile 投影；Frame/Render 的 Pipeline、Feature、Pass 为兼容视图，Logic/Process 的 State/Transition 为 Feature-owned 子图 |
| Domains              | Render、Logic、Physics、Audio、Stream 等 |

### 4.2 输入输出契约

每个端口定义：

- PortId 和显示名。
- Input/Output 方向。
- DataType、ValueSchema/SchemaVersion、Domain、Scope、Lifetime、Access。
- 是否必填、默认值和默认资源。
- 允许的来源模式：上游数据边、项目资产、默认值、运行上下文或它们的显式二选一。
- 外部绑定的身份格式和解析规则，例如稳定 AssetId、资源类别和导入状态。
- 单输入、可选输入或节点专属 Variadic/Array 组。
- 最小/最大来源数量、槽位身份、是否有序。
- 格式、尺寸、采样、颜色空间、缓冲布局等限制。
- 是否允许分叉、是否需要复制、是否允许外部输入。
- 允许的 Adapter 类型。
- 是否可以暴露为子图接口。

节点实例只能连接这些已声明的端口。端口数量不是画布自由度，而是节点行为定义的一部分。

### 4.3 参数契约

参数定义类型、默认值、单位、范围、枚举、是否影响拓扑、是否影响端口模式、是否需要重新准备资源和是否允许运行时修改。

参数可以影响节点的值，但只有节点明确声明“参数会产生哪种接口变体”时，才允许改变输入输出集合。例如 `Bloom.Layered` 的 `LayerCount` 可以在 1..3 范围内控制已声明的 Layer 槽位；普通 `Bloom.Basic` 没有这个参数，不能由编辑器自行添加。参数也不能把一个只允许数据边的端口临时改成文件输入；来源模式属于节点契约。

### 4.4 执行契约

节点定义：

- 何时可以执行：需要哪些输入、是否等待全部来源。
- 执行后产生哪些输出和完成信号。
- 每个输出的 CompletionDomain、CompletionStage、ResultStatus 和结果身份。
- 是否有外部副作用、写入目标或状态变更。
- 副作用的 CommitPolicy、RetryPolicy、幂等性和状态迁移策略。
- 所属 Stage/Phase、ExecutionDomain 和允许 Queue。
- 是否允许裁剪、合并、缓存或多次执行。
- 是否支持 Preview、Cook、Runtime、Editor-only。
- 失败时返回什么诊断以及哪些输出无效。

普通数据边形成 `A 先于 B` 的依赖。节点不需要通过隐藏顺序属性改变数据边；只有固定的引擎阶段和资源同步规则可以对图施加额外约束。

### 4.5 资源契约

节点声明创建、读取、写入、导入、导出或保留哪些资源。资源契约至少包括资源类别、格式、尺寸策略、所有权、生命周期、读写权限、别名/复用限制和调试可见性。

编辑器不能把两个同名纹理自动当作同一资源，也不能把输出端口名称相同的两个 Pass 自动合并。绑定必须使用稳定 ResourceId/ArtifactId。

### 4.6 编辑能力契约

节点还要声明：

- 是否可以被用户添加。
- 是否可以复制、删除、替换。
- 哪些参数可编辑。
- 哪些端口可重连。
- 是否允许作为子图。
- 是否允许暴露输入/输出。
- 是否允许跨 Pipeline/Feature 连接。
- 是否仅能在特定 Feature/Part 或目标中使用。

`allow_add_passes` 只适用于 RenderFeature 的 Frame/Render Pass 集合由作者文档负责：作者可以保留、删除、增加和重排声明允许的 Pass 类型，
同一类型的不同实例也必须保持各自的实例身份。它不等于可以修改 Pass 的执行契约；队列、参数、资源绑定、输出语义和跨 Part
移动仍必须由 Feature 的声明与运行时适配器分别验证。内置 Deferred/Forward Renderer 将默认 Pass 作为可编辑模板，显式 Feature
下删除最后一个 Pass 也必须保持为空；删除必需 Pass 或断开必需数据流时，编译器必须给出诊断，不得偷偷恢复固定默认图。

## 5. 节点如何进入节点库

### 5.1 注册成功不等于当前可用

节点库按以下条件筛选：

1. 当前模块是否已加载。
2. 当前图层是否允许该节点。
3. 当前父 Pipeline/Feature/Part 是否授权。
4. 当前 Domain、Scope、FeaturePoint、Queue 和目标是否兼容。
5. 当前节点是否被项目配置或平台禁用。
6. 节点是否是用户当前操作需要的输入/输出类型。

不满足条件的节点可以在“显示全部”中查看，但必须给出原因，如“该 Feature 只允许在 Render Part 中使用”或“当前目标不支持该格式”。

### 5.2 从端口打开候选节点

从一个输出端口拖到空白处时，节点库按照输出 DataType、Domain、Scope、Lifetime 和目标上下文筛选“可接收节点”。候选卡片显示它要接收的具体端口，而不是只显示节点名称。

从一个输入端口拖到空白处时，节点库列出能产生该端口类型的节点，并显示它们需要的上游输入。没有合法候选时提供外部资源、Graph Input 或查看契约错误入口，但不强行创建一个未知节点。

### 5.3 搜索结果必须可解释

搜索 `Bloom` 时结果至少显示：来源模块、节点类型、可用图层、输入摘要、输出摘要、是否可编辑、是否需要额外资源、目标限制和版本。显示名相同的节点按模块和 TypeId 区分，不按名称合并。

## 6. 一个节点的完整定义示例

下面是产品设计层的 `Bloom.Layered` 示例，用于说明功能如何确定，不是实现代码：

| 项目           | 定义                                                                                                                                                                                                                                |
|----------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 来源           | Game.Render.PostProcess 模块                                                                                                                                                                                                        |
| 类型           | RenderPass                                                                                                                                                                                                                          |
| 用途           | 根据场景颜色和亮度遮罩生成 Bloom 颜色                                                                                                                                                                                               |
| 可用图层       | Feature Graph、Pass Graph                                                                                                                                                                                                           |
| 固定输入       | SceneColor：必需获得来源，Texture2D<Color>，最多 1 条数据边，允许 `EdgeOrAsset`；BrightnessMask：必需获得来源，Texture2D<Scalar>，最多 1 条数据边，允许 `EdgeOrAsset`；Exposure：可选，Float，最多 1 条数据边，允许 `EdgeOrDefault` |
| 节点专属多输入 | AdditionalLayers：0..3 个 Texture2D<Color>，每项单独进入合成层；只有 Layered 变体拥有该组                                                                                                                                           |
| 输出           | BloomColor：Texture2D<Color>；Completion：ExecutionToken                                                                                                                                                                            |
| 参数           | Intensity、Threshold、Knee、LayerWeights[0..2]                                                                                                                                                                                      |
| 资源约束       | Frame Scope、Transient Color Texture、允许跟随 View 尺寸                                                                                                                                                                            |
| 执行规则       | 等待已满足的必需来源和所有已连接的 Layer 输入；资产绑定由 Prepare/Cook 提供，不虚构上游执行节点；结果产生后下游才能执行                                                                                                             |
| 副作用         | 无外部副作用，可被裁剪但需保留调试输出引用                                                                                                                                                                                          |
| 编辑能力       | 可添加、复制、删除、改参数、重连；不能增加第四个 Layer                                                                                                                                                                              |
| 目标限制       | 支持 Graphics Queue；不支持没有颜色纹理能力的目标                                                                                                                                                                                   |
| 版本策略       | 新增输入或改变默认合成顺序时提高版本并提供迁移                                                                                                                                                                                      |

从这个定义，编辑器自动得到：节点卡片长什么样、有哪些端口、每个端口能接什么、能否增加槽位、删除会影响什么、何时能编译和如何进入运行实现。没有这份定义，编辑器不应显示该节点。

### 6.1 Texture 资产来源示例

一个 `TextureAsset` 节点可以没有输入端口，只有一个 `Asset` 参数和一个 `Texture` 输出。用户在资源选择器中选择 `Assets/Textures/BloomMask.png` 后，编辑器保存稳定 AssetId，节点输出可通过普通数据边连接到下游 Pass。这个节点的连线仍然同时表示纹理数据和生产者先后；文件路径只是资产身份的编辑入口，不是额外的顺序线。

对于简单节点，也可以把 `EdgeOrAsset` 端口直接放在节点检查器里：有数据边时使用上游结果，切换到 Asset 模式时解除该边并绑定 AssetId。两种来源必须显式切换，不能同时存在后让引擎猜优先级。

## 7. 节点功能的确定责任

### 节点设计者负责

- 用户能理解的用途和名称。
- 输入输出的业务语义。
- 输入数量、可选性、默认值和多源规则。
- 数据类型、资源约束、作用域和生命周期。
- 输出结果和执行先后含义。
- 参数范围、性能成本和失败诊断。
- 版本升级和接口迁移策略。

### 引擎负责

- 校验契约结构完整性和身份唯一性。
- 校验连接、类型、Scope、Lifetime、数量和循环。
- 根据数据边生成执行依赖和准备计划。
- 把节点实例映射到注册的运行实现。
- 保护固定边界和最后可用运行态。
- 在运行检查中回溯节点来源。

### 游戏开发者负责

- 选择节点和数据来源。
- 配置公开参数和节点允许的输入槽位。
- 处理断线、格式冲突和目标限制。
- 通过图组合出目标功能，不修改节点的底层执行实现。

## 8. 注册、审核和发布状态

节点进入团队可用目录前经历四个状态：

1. **Draft**：节点契约设计中，只能在开发者模式或示例项目中看到。
2. **Validated**：目录和运行实现通过契约校验，可被测试图使用。
3. **Project Available**：已注册到当前游戏模块，按目标和权限出现在节点库。
4. **Deprecated/Unknown**：旧版本仍可读取，但新图不推荐使用；迁移或替换后再保存。

节点的契约变更需要分类：

- 只改显示名、说明或图标：不影响运行语义。
- 改默认参数：需要显示新旧默认值。
- 新增可选输入/输出：通常兼容，但要保持旧实例行为。
- 新增必填输入、删除端口、改变类型或输入数量：必须迁移并重新验证。
- 改变输出含义、资源生命周期或执行阶段：作为不兼容版本处理。

## 9. 节点来源与运行实现的边界

一个节点在编辑器中是“类型契约 + 实例参数 + 数据边”；在运行时是“注册实现 + 准备资源 + 当前输入 + 执行结果”。编辑器不保存函数地址、编译索引、GPU Handle 或设备对象，只保存稳定 TypeId、Version、NodeId、参数、端口连接和布局。

这也是为什么不能通过源码扫描自动生成节点：源码可以存在函数，但没有稳定的用户输入输出、参数范围、资源生命周期、版本迁移和错误解释。只有完成注册契约的功能，才有资格成为图中的积木。

## 10. 双击节点与代码边界

本节给出统一入口和边界原则；自定义代码节点的脚手架、IDE 项目解析、契约回流和验收流程见 [自定义节点开发工作流](custom-node-development.md)。

### 10.1 结论：要做，但双击语义应是“打开节点定义”

建议实现双击入口，但不要把所有节点的双击都固定为“打开外部 IDE”。同一个节点画布同时承载图资产节点、代码实现节点、引擎系统节点和运行时只读节点，它们的定义位置不同。双击统一表示“查看/进入这个节点的定义”，再按节点来源路由到正确的工作区：

| 节点来源                                   | 双击默认目标                       | 是否打开外部 IDE                     |
|--------------------------------------------|------------------------------------|--------------------------------------|
| Graph Asset、Feature、CompositePass、Macro | 进入子图编辑器                     | 否                                   |
| 游戏项目代码节点                           | 节点定义工作区，并定位到代码边界   | 有源码映射和编辑权限时提供“打开 IDE” |
| 引擎/领域模块节点                          | 契约、文档、来源模块和只读实现信息 | 默认不打开；可按权限打开源码         |
| Unknown/Offline 节点                       | 缺失模块、版本和原始字段诊断       | 不打开，提供模块定位或迁移入口       |
| Reroute、Comment、Runtime Inspect 节点     | 属性或运行来源面板                 | 否                                   |

这样既保留双击进入子图的 UE 风格体验，又不会让用户误以为每个 Pass 都有可以编辑的独立代码文件。外部 IDE 是代码节点定义工作区中的一个动作，不是所有节点的共同实现方式。

### 10.2 自定义代码节点的“定义工作区”

对自定义 Pipeline、Feature、Pass 节点（以及未来开放的 Logic/Flow State/Transition 节点），编辑器应提供一个节点定义工作区，至少显示：

1. **身份**：TypeId、版本、实例 NodeId、OwnerModule、当前目标和加载状态。
2. **契约**：输入输出端口、基数、参数、资源约束、执行阶段、队列和编辑能力；这些内容来自 TypeCatalog，不允许在节点实例上直接改成另一套语义。
3. **代码边界**：注册入口、契约声明位置、准备/编译入口、运行入口、诊断入口和源文件/符号位置。
4. **动作**：查看文档、复制 TypeId、打开源码、重新加载模块、比较契约版本、查看受影响图资产。
5. **状态**：源码不存在、模块未加载、构建失败、契约变更待迁移、只读或编辑权限不足。

“打开 IDE”应定位到具体文件和符号，例如节点注册处、契约声明处或执行入口；不能只打开项目根目录。编辑器仍以 TypeCatalog 的契约为准，IDE 中的代码修改只有在重新构建、重新注册并通过契约校验后，才会影响节点库和图编译。

### 10.3 代码边界需要显式映射

代码节点的注册信息需要补充一组源映射元数据：

| 元数据         | 作用                                          |
|----------------|-----------------------------------------------|
| DefinitionKind | Code、GraphAsset、System、External 等定义类型 |
| ContractSource | 契约声明文件、模块或生成来源                  |
| SourceUri/File | 可定位的源码文件或工程 URI                    |
| Symbol         | 类型、注册函数、准备入口或执行入口            |
| BuildTarget    | 需要重新构建的模块/目标                       |
| Editability    | 可编辑、只读、仅文档或不可用                  |
| ReloadPolicy   | 重载目录、重启编辑器或必须重启游戏            |
| DebugMapping   | Runtime Inspect 回到源码和作者节点的映射      |

这些信息只用于导航、诊断和回溯，不写入运行时函数地址，也不让作者图依赖本地绝对路径。项目迁移到另一台机器时，使用工程相对路径、模块名和符号重新解析。

### 10.4 实例与类型必须分开

双击一个节点实例打开的是它所属的 **节点类型定义**，不是为这个实例复制一份代码。多个 `OutlinePass` 实例共享同一个 TypeId 和实现，但各自拥有参数、资源绑定和数据边。

如果项目确实要对某个实例做专用实现，必须使用显式的“派生节点/本地化节点”动作，生成新的 TypeId 或图资产版本，并重新声明端口与迁移关系。不能通过双击后直接修改共享类型，避免一个节点的代码改动悄悄影响全项目实例。

### 10.5 从 IDE 返回编辑器的契约变更流程

代码修改不应直接改写作者图。推荐回流流程：

```text
IDE 保存源码
    → 构建项目模块
    → 重新导出 TypeCatalog
    → 比较旧/新 Node Contract
    → 生成端口、参数和行为迁移预览
    → 用户确认后重新编译受影响图
```

迁移预览至少区分：

- 只改说明、图标或源码位置：无需迁移。
- 修改默认值：显示受影响实例的新旧值。
- 新增可选端口或上限未变的可变槽位：保留旧图行为。
- 新增必填端口、删除/重命名端口、改变类型或改变输入数量：标出断边和阻断编译的实例。
- 改变输出含义、资源生命周期、阶段、队列或副作用：提高契约版本，要求重新验证，不能仅按字段名自动迁移。

构建失败时，节点继续保留上一次有效契约和上一次可用运行态；图可以离线编辑，但节点状态显示“源码已变更、目录未更新”或“模块构建失败”。新契约导致的输入来源未满足不能被自动接到相似资源上；合法的资产绑定、默认值或上下文来源也必须经过用户确认。

### 10.6 权限和安全边界

双击代码节点前检查项目权限、源码可用性和当前编辑模式：

- 游戏开发者可以查看契约、参数和文档；是否能改源码由项目权限决定。
- 只读模块只显示源码位置和版本，不提供写入动作。
- 没有安装外部 IDE 时，仍可打开契约工作区，并复制源码定位信息。
- 外部 IDE 关闭、构建超时或重载失败不能撤销作者图，也不能删除当前节点。
- 代码节点禁止把 GPU Handle、函数指针或本机绝对路径保存到 `.aegpipe`。

## 11. 设计完成标准

节点系统只有满足以下条件才算设计闭环：

- 每个可见节点都能回答“来自哪个模块、做什么、需要什么、产生什么、能否运行”。
- 节点库能按当前图层、父级权限和端口类型筛选。
- 节点输入数量来自契约，不由拖线猜测。
- 每条普通连线同时建立数据流和执行先后。
- 节点实现缺失时保留作者数据并显示原因。
- 版本升级能说明哪些边和参数需要迁移。
- 同一契约在编辑器验证、编译计划和运行时执行中含义一致。
