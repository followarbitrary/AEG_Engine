# AEG FlowGraph：自定义节点开发工作流

[返回架构总览](<../AEG FlowGraph Architecture.md>)

契约导出、ContractDigest、模块代次和状态迁移以 [作者与执行契约](authoring-and-execution-contract.md) 为准；本分册展开 IDE、脚手架和代码回流交互。

## 1. 研究问题与结论

要回答的不是“能不能双击打开 IDE”，而是四个边界问题：

1. 双击的是节点实例，还是节点类型定义？
2. 哪些节点有代码实现，哪些节点只有子图或资源定义？
3. 代码、Node Contract、TypeCatalog 和 `.aegpipe` 谁是唯一真源？
4. IDE 修改后，如何安全地回到编辑器并影响节点库和已有图？

结论是：**应该支持统一的“打开节点定义”入口，并为自定义代码节点提供“在 IDE 中打开”和“生成实现”动作；不应该让所有节点双击都直接打开 IDE，也不应该允许双击节点实例后直接改共享实现。**

推荐采用四种定义方式；其中 Pipeline/Pass 仅是 Frame/Render 兼容 profile 的代码或投影节点：

| 节点类型                                   | 定义位置           | 双击默认行为                   | 是否生成代码     |
|--------------------------------------------|--------------------|--------------------------------|------------------|
| Graph Asset、Feature、Composite（Render 子图含 CompositePass） | 子图资产 | 进入子图编辑器 | 否 |
| 自定义代码 Feature；Frame/Render 兼容的 Pipeline/Pass | 游戏项目模块源码 | 打开节点定义工作区，可定位 IDE | 是 |
| 引擎系统和领域内置节点                     | 引擎/领域模块      | 查看契约、文档和只读来源       | 仅模块开发者可改 |
| Runtime Inspect、Unknown、离线节点         | 运行快照或缺失模块 | 打开诊断和来源追踪             | 否               |

“双击”表达的是**进入定义**，IDE 只是代码定义节点的一个后续动作。新建代码节点则使用显式的“创建自定义节点”向导；编辑已有节点实例时，默认进入的是它所属的共享类型，不会偷偷复制一份代码。

## 2. 与当前 AEG 工程的对齐

当前工程已经有以下基础，方案应继续沿用，不再创建第二套节点目录：

- `TypeCatalog`、`TypeCatalogEntry`、`PortDescriptor`、`ParameterDescriptor` 和 `AuthoringDeclaration` 是编辑器可见契约的基础。
- 游戏模块通过稳定 TypeId、OwnerModule 和版本注册 Feature；当前实现仍兼容注册 Frame/Render
  profile 的 Pipeline、Feature、RenderPass。
- 编辑器可以读取 `Source/GameModule.metadata.json` 或构建产物中的 `module.metadata.json`，不需要先加载 DLL 才能绘制节点库。
- 游戏项目模板把自定义渲染扩展放在 `Source/Render/`，Pipeline 文档放在 `Assets/Pipelines/`。
- `.aegpipe` 只保存稳定类型身份、实例参数、端口连接、资源绑定和布局，不保存函数地址、GPU 句柄或本机绝对源码路径。

因此，第一阶段的唯一真源建议是：**模块中的节点契约声明和注册代码**。TypeCatalog 元数据由构建/导出流程生成，编辑器只消费元数据；`.aegpipe` 只保存节点实例。以后可以把契约声明迁移到声明式 `.aegnode` 文件，但不能让 C++、`.aegnode` 和编辑器面板同时独立修改同一组端口，否则一定会出现节点库和运行实现不一致。

## 3. 为什么不能把所有节点双击都直接打开 IDE

### 3.1 双击节点实例不等于编辑节点实现

一个 `OutlinePass` 类型可以在几十张 Pipeline 图中被实例化。双击其中一个实例，打开的应该是共享的 `OutlinePass` 类型定义；修改实现会影响所有实例，编辑器必须明确显示影响范围。

如果用户只想改变某一处效果，应使用以下之一：

- 修改当前实例的参数或数据边。
- 复制为新的图资产节点。
- 执行“派生节点/本地化节点”，生成新的 TypeId 和独立实现。

不能让用户在双击后直接修改共享代码，再让所有同类型节点无提示地发生变化。

### 3.2 不同节点的定义位置不同

- Feature 图资产没有独立 C++ 执行函数，双击应进入内部子图。
- 系统节点可能由引擎固定提供，用户只能查看契约。
- Runtime Inspect 节点是编译后的观察对象，不是作者资产。
- Unknown 节点缺少模块实现，打开 IDE 没有可靠目标，应该先显示缺失模块和原始字段。

统一的“打开节点定义”路由可以覆盖这些情况，而“直接打开 IDE”不能覆盖。

## 4. 推荐交互入口

### 4.1 双击入口

双击节点后先进入“节点定义工作区”，工作区顶部显示：

1. TypeId、类型版本、实例 NodeId、OwnerModule。
2. 当前项目、目标平台、模块加载状态和契约状态。
3. 输入输出端口、输入基数、参数、资源约束和执行阶段。
4. 当前类型被多少图和多少节点实例使用。
5. 最近构建状态、目录版本和受影响图。

代码节点在工作区提供明确的按钮：

- **在 IDE 中打开契约声明**。
- **在 IDE 中打开执行入口**。
- **在 IDE 中打开模块注册入口**。
- **重新构建模块并刷新 TypeCatalog**。
- **比较当前契约与上一次有效契约**。
- **查看受影响图和迁移预览**。

双击代码节点不直接执行构建、不自动改图、不自动升级端口。这样用户能先看清“这是共享类型”以及“代码修改会影响哪些实例”。

### 4.2 新建自定义节点入口

节点库和画布右键提供“创建自定义节点”，不要把这个功能隐藏在已有节点的双击行为里。向导分为以下步骤：

```text
选择节点种类
    → 选择项目模块和领域
    → 定义 TypeId、显示名和版本
    → 定义端口、输入基数和参数
    → 选择代码模板与文件位置
    → 生成预设文件
    → 打开 IDE
    → 构建并导出 TypeCatalog
    → 契约差异检查
    → 节点进入可用目录
```

向导在生成前必须显示“将创建哪些文件、将修改哪个模块、将影响哪个构建目标”。用户可以取消生成；取消不能留下半成品节点，也不能把未注册的临时类型写入 `.aegpipe`。

### 4.3 右键菜单

| 操作          | 适用对象                           | 结果                       |
|---------------|------------------------------------|----------------------------|
| 打开节点定义  | 所有有稳定类型的节点               | 进入契约、来源和状态工作区 |
| 进入子图      | Graph Asset/Composite 节点         | 打开内部图                 |
| 在 IDE 中打开 | 有源码映射且用户有权限的代码节点   | 定位到文件和符号           |
| 创建实现      | 只有契约、没有代码实现的自定义类型 | 生成代码脚手架             |
| 派生节点      | 需要独立语义的代码节点             | 生成新 TypeId 和迁移副本   |
| 查看契约差异  | 已重新构建但目录未应用的节点       | 显示端口、参数和行为变化   |
| 重新加载模块  | 目录或模块状态异常                 | 保留作者图，刷新目录和诊断 |

菜单项不可用时显示原因，例如“当前类型来自只读引擎模块”“项目未打开”“没有源码映射”“模块构建失败”。

## 5. 代码脚手架生成设计

### 5.1 生成目标

生成的不是“当前节点实例的代码”，而是一个可被多个实例复用的**节点类型实现模板**。代码至少分成四个概念边界：

1. **契约声明**：TypeId、版本、端口、参数、资源、来源模式和能力。
2. **准备/编译入口**：把作者图输入转换为运行时资源和执行计划。
3. **执行入口**：消费已验证的输入，产生声明的输出。
4. **诊断和来源映射**：把失败回溯到端口、参数、源码和作者节点。

建议生成以下项目相对路径，实际目录由模块模板决定：

```text
Source/Render/<Pipelines|Features|Passes>/<NodeName>/
    <NodeName>.hpp              # 人工维护的公开类型声明
    <NodeName>.cpp              # 人工维护的契约和执行实现
    <NodeName>.node.json        # 可选的生成摘要，不作为第二份契约真源
Source/Generated/<Module>/
    <Module>.pipeline_nodes.cpp # 生成的注册聚合入口
```

第一阶段如果必须兼容当前 `GameModule.cpp` 注册方式，可以生成带明确标记的注册区；生成器只能更新标记区，不能覆盖用户文件的其他内容。更稳妥的长期方向是把节点注册聚合到独立的生成文件，再由模块入口调用，避免反复生成时改写人工代码。

### 5.2 代码模板的固定区域和可编辑区域

模板应明确标出以下内容：

- `TypeId`、OwnerModule 和初始版本由生成器写入，但允许用户在向导中确认。
- 端口、来源模式和参数的契约声明由向导生成；用户可以在 IDE 修改，但修改必须经过契约差异检查。例如 `Texture2D` 输入可以声明 `EdgeOrAsset`，表示既能接上游纹理结果，也能绑定稳定 AssetId；没有这个声明时，编辑器不能把端口改成文件选择器。
- 执行函数、资源准备和诊断函数由用户实现。
- 生成摘要和注册聚合文件不允许手工写入与契约不一致的值。
- 文件头写入生成来源、模板版本和重新生成提示，避免用户误以为所有内容都可安全覆盖。

生成器必须幂等：重复打开向导或刷新节点不能覆盖已有实现文件。检测到文件存在时，只能选择“打开现有实现”“生成新 TypeId”或“比较模板差异”。

### 5.3 三种节点模板

| 模板          | 适用场景                                                | 生成内容                                   | 首期要求 |
|---------------|---------------------------------------------------------|--------------------------------------------|----------|
| Pipeline Node | 需要定义阶段、FeaturePoint、公开输入输出的高层 Pipeline | Pipeline 契约、边界和编译入口              | 支持     |
| Feature Node  | 组合多个 Pass 或资源，形成游戏能力                      | Feature 契约、默认 Pass、可选子图/执行入口 | 支持     |
| Pass Node     | 读取/写入资源并执行具体渲染步骤                         | Pass 契约、资源声明、准备和执行入口        | 优先支持 |

Feature 如果只是图资产，不应强制生成 C++；向导要先让用户选择“图资产 Feature”还是“代码 Feature”。

## 6. IDE 自动打开与项目解析

编辑器侧的脚手架入口已经固定为 `editor_custom_node_workflow.hpp` 中的
`scaffold_custom_node`。它接收已经通过 `TypeCatalog` 校验的 Pipeline、Feature 或 Pass
契约，在工程根目录下生成四个可审查文件：`*.flowgraph.hpp`、`*.flowgraph.cpp`、
`*.flowgraph.registration.cpp` 和 `*.flowgraph.contract.json`。生成器只接受工程根目录下的
相对源码目录，拒绝 `..`、绝对越界路径和非法 C++ 类型名；覆盖必须显式开启，多个文件使用
同一批临时文件与备份完成提交，失败时回滚。返回值包含契约文件、实现函数和注册函数的文件、
行号与符号，因此 IDE 集成层可以定位到定义，而不需要让编辑器直接启动某一种 IDE。

生成的注册文件只提供 `AEG_REGISTER_PIPELINE`、`AEG_REGISTER_FEATURE` 或
`AEG_REGISTER_RENDER_PASS` 的调用入口；节点的 TypeId、Owner Module、版本、端口来源规则和
Variadic 组同时写入契约 JSON。源码模板只建立编译边界和空执行体，实际业务逻辑仍由游戏开发者
在 IDE 中实现，构建后再由模块元数据回流 TypeCatalog。

### 6.1 项目解析顺序

编辑器应按以下顺序确定 IDE 和项目：

1. 当前显式打开的 `Project.aegproj` 根目录。
2. 节点 `OwnerModule` 对应的模块目标和源码根目录。
3. 工程配置中声明的 IDE/编辑器偏好。
4. 当前平台的文件关联或用户选择的 IDE。

不要通过扫描磁盘寻找“看起来像项目”的目录，也不要使用源码文件中的绝对路径作为长期映射。源映射保存工程相对路径、模块名、目标名和符号名；换机器后重新解析。

### 6.2 IDE 打开目标

不同动作应定位到不同符号，而不是只打开项目根目录：

| 动作         | 定位目标                               |
|--------------|----------------------------------------|
| 打开契约声明 | `TypeCatalogEntry` 或节点声明函数      |
| 打开执行入口 | Pass/Feature/Pipeline 的执行或准备函数 |
| 打开注册入口 | 模块注册函数或生成注册聚合文件         |
| 打开诊断     | 节点诊断函数、错误码或来源映射         |
| 打开生成文件 | 生成摘要和模板版本，不允许误当人工实现 |

如果 IDE 未安装，仍然打开节点定义工作区，并提供复制路径、复制符号和打开系统文件管理器的动作；不能因此让节点变成 Unknown。

### 6.3 项目未打开或模块未加载

- 没有打开项目：双击只能显示节点契约；“打开 IDE”按钮提示需要打开项目。
- 模块 metadata 存在但 DLL 不在：可以显示节点和源码映射；不能执行预览。
- 源码存在但 metadata 过期：显示“源码已变更、目录未更新”，先构建再刷新。
- 模块构建失败：保留上一次有效 TypeCatalog 和运行态，当前节点标记为构建失败。
- 源码被移动：按模块和工程相对路径重新解析；无法解析时显示待修复映射，不删除作者节点。

## 7. 代码修改回流编辑器

代码不是保存后立即生效，而是经过可复核的回流流程：

```text
IDE 保存
    → 构建项目模块
    → 生成/更新 module.metadata.json
    → 导出新的 TypeCatalog
    → 对比旧 Node Contract
    → 生成迁移预览和受影响图列表
    → 用户确认应用目录
    → 重新验证和编译作者图
    → 预览通过后才可应用运行态
```

### 7.1 契约差异分类

| 变化                                           | 处理方式                                                     |
|------------------------------------------------|--------------------------------------------------------------|
| 显示名、说明、图标、源码位置                   | 可热刷新，不改变图语义                                       |
| 默认参数变化                                   | 显示新旧默认值，不自动覆盖已有实例值                         |
| 新增可选端口                                   | 保留旧图，要求用户决定是否连接                               |
| 可变输入上限增加                               | 保留旧槽位，允许新槽位在新实例中使用                         |
| 新增必填端口                                   | 阻止受影响图编译，要求补边、提供合法外部绑定或提供声明默认值 |
| 端口删除、重命名、类型变化                     | 生成断边和迁移建议，不能按显示名自动连接                     |
| 输入数量规则变化                               | 提高契约版本，逐图检查连接数量                               |
| 输出含义、资源生命周期、阶段、队列或副作用变化 | 作为行为不兼容变更，要求重新验证                             |

### 7.2 版本与实例影响

节点类型版本和节点实例版本分开：

- `TypeId + ContractVersion` 标识一套可执行语义。
- `NodeId` 标识图中的一个实例。
- 节点实例保存创建时的契约版本、参数和连接快照。
- 新类型版本可以提供迁移器，但不能静默替换旧实例。

编辑器应显示“当前实例使用已锁定契约，目录已有新契约”，并允许用户查看迁移前后端口和参数差异。

## 8. 权限、安全与团队协作

代码节点需要比普通图编辑更高的权限边界：

- 游戏开发者可以创建节点实例、配置参数和打开源码；是否允许修改模块源码由项目权限决定。
- 只读引擎模块只能查看契约和源码位置。
- 生成器不得覆盖人工实现文件、不得删除节点目录、不得把本机绝对路径写入图资产。
- 构建和模块重载失败时保留 last-good 目录与运行态。
- 代码修改必须经过现有工程构建、metadata 校验和作者图验证，不能由编辑器绕过构建直接加载任意 DLL。
- 团队共享的是 TypeId、契约版本、模块源文件和迁移记录；不是某台机器上的 IDE 配置或函数地址。

## 9. 首期范围

### 首期应支持

1. 双击节点进入“节点定义工作区”。
2. 对有源码映射的项目代码节点提供“在 IDE 中打开”。
3. “创建自定义 Pass”向导，生成契约/实现/注册脚手架。
4. 复用当前 `TypeCatalog`、模块 metadata 和工程 `Source/` 路径。
5. 构建后 TypeCatalog 刷新、契约差异、迁移预览和 last-good 保留。
6. Feature 同时支持“图资产”与“代码 Feature”两种明确模式。

### 当前不开放

- 双击任意节点直接修改共享实现。
- 在画布上临时创建没有 TypeId 的匿名代码节点。
- 由编辑器自动扫描任意 C++ 函数生成节点。
- 让 `.aegpipe` 直接保存源码片段或编译产物句柄。
- IDE 保存后绕过模块构建和契约验证自动应用运行态。
- 让一个节点实例的“本地修改”悄悄改变同类型的其他实例。

## 10. 验收场景

### 场景 A：创建自定义 Pass

游戏开发者在 Pass 节点库选择“创建自定义 Pass”，填写 `Game.Render.OutlinePass`、两个固定输入、一个可选参数和一个颜色输出。向导生成项目相对源码、注册入口和模板文档，自动打开当前游戏项目的 IDE。首次构建后节点出现在目录中，放入图后普通数据边同时形成输入依赖和执行先后。

### 场景 B：修改已有 Pass 的输入

开发者在画布双击 `OutlinePass`，进入节点定义工作区，再打开 IDE 修改契约。构建完成后，编辑器显示新增端口和受影响图；没有数据边、合法外部绑定、默认值或上下文来源的新必填端口，图保持可保存但不能编译。用户补齐来源并确认迁移后，预览才能使用新契约。

### 场景 C：只修改一个实例

开发者不打开共享代码，而是修改实例参数，或执行“派生节点/本地化节点”。系统生成新的 TypeId/版本后，只有新实例使用新实现，原有图不受静默影响。

### 场景 D：模块暂时不可用

项目打开时模块 DLL 被重命名，编辑器仍从 `module.metadata.json` 显示节点和已有连线。双击进入契约和诊断工作区；重新构建模块并恢复合法 manifest 后，节点回到可预览状态，作者图无需重建。

## 11. 完成标准

这项功能只有满足以下条件才算闭环：

- 双击语义统一为“打开定义”，并按节点来源路由。
- 代码编辑针对节点类型，不针对单个实例偷偷复制实现。
- 自定义节点可通过向导生成项目内预设代码和注册入口。
- IDE 能定位到契约、注册、执行和诊断符号。
- TypeCatalog 是编辑器目录和运行验证的共同契约来源。
- 源码修改必须经过构建、契约差异、迁移和图验证。
- 构建失败或模块离线时保留 last-good 节点目录、作者图和运行态。
- 固定输入、命名输入和节点专属可变输入规则不因代码生成而被绕过。
- 必需输入可以由上游数据边、资产、默认值或运行上下文满足，但来源模式必须由节点契约明确声明。
- 普通数据边仍同时表达数据流与执行先后。
